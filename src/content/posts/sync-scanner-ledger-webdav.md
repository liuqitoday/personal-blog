我的 NAS 是单盘的，云端是唯一的异地副本。这事本来交给群晖自带的 Cloud Sync，直到我发现：**每次它启动，都要花两个半小时把远端目录逐层对账一遍**，而这台机器本地完整遍历所有文件只要 33 秒。

更麻烦的是，我当时刚因为上行流量被运营商按 PCDN 判定限速、断了几天网，解封不久。所以这次改造的第一约束不是"快"，而是**一个字节都不能重复上传**。

## 先把问题量清楚

开机之后，从 Cloud Sync 的日志里按会话统计 `rescaning directory` 的时间范围：

```text
两个 homes 会话：各扫描 6000+ 个目录，耗时都在 2.5 小时左右
其中一个是"仅上传"方向，耗时和双向几乎一样
同一台机器上 find 全树（排除 @eaDir）：33 秒
```

结论很清楚：

- **启动对账跟同步方向无关**。把任务改成"仅上传"并不会让它跳过远端比对。
- 时间几乎全花在 WebDAV 的远端列举上，不在本地磁盘。
- 两个时间段的 WebDAV 上传 URL 集合交集为 0——启动扫描**不会**重传文件。也就是说，它只是慢，不是危险。

但"只是慢"在单盘 NAS 上就够危险了：两个半小时里，任何一次重启、任何一次套件更新，备份窗口都被吃掉，而且这段时间里你根本不知道它跑到哪了。

## 现成方案为什么都不行

| 方案 | 结论 |
| --- | --- |
| Cloud Sync 保持现状 | 每次启动都全量对账，改方向无效 |
| Kopia / restic / Duplicati | 仓库格式接不了云端已有的明文文件，首次必须全量上传 |
| rclone 单独用 | 没有持久索引，每次仍要列远端；WebDAV 的 mtime 不可靠，默认比较会反复重传 |
| Hyper Backup | DSM 的目标列表里没有 WebDAV |
| Syncthing | 不能对接 WebDAV，而且启动也做 initial scan |

我需要的其实是一个很薄的东西：**一份"哪些文件已经传过"的本地账本，加一个每天跑一次的上传编排**。没有实时同步、没有版本历史、不改远端、不删远端。

## 设计：只信本地，不碰远端

核心只有三条：

1. **本地 SQLite 记账**。文件身份是 `(source, 相对路径)`，变化依据是 `size + mtime_ns`。每个目的地、每个映射分别记录"最后一次确认成功时的元数据"。
2. **日常运行绝不枚举远端**。扫描只看本地元数据；账本算出待传清单，交给 `rclone copy --files-from-raw --no-traverse`。没有变化就根本不启动 rclone。
3. **成功后先确认再记账**。rclone 报告传输完成后，重新 stat 本地文件，元数据没变才在事务里写 `ok`。

对已经由 planner 选中的文件，额外加 `--ignore-times`：纯 WebDAV 不保留 mtime，如果让 rclone 用默认的 size+mtime 判断，同尺寸的内容修改会被跳过。

## 首次接管：从 Cloud Sync 自己的索引里"偷"状态

这是整个项目最省事的一步。Cloud Sync 不提供导出，但它自己的 SQLite 里什么都记着：

```text
/volume1/@cloudsync/session/<id>/event-db.sqlite   → event_info
  path / file_type / local_mtime / local_file_size / file_size / mtime
```

`local_mtime` 和 `local_file_size` 跟磁盘 `stat` 的结果抽样 20/20 完全一致。所以我做了 `adopt --mode cloud-sync`：只读地把这些记录灌进账本，把"本地路径 + 大小 + mtime + 远端大小"完全一致的文件标记为已上传，再从本地和远端共有的文件里抽样 `stat` 验证路径映射。全程不上传、不列远端目录树。

接管完成后 `plan` 是 0，第一次真实运行也是 0 上传。这才敢换掉 Cloud Sync。

对于没有 Cloud Sync 索引的目的地，还有一个 `--mode remote`：只读列一次远端清单，按路径和大小匹配同样可行，代价是要等一次完整 PROPFIND。

## 几个必须做对的细节

**1. `/dav` 写重了就是一整轮全量重传。** OpenList 这类 WebDAV 服务的 URL 本身已经带了 `/dav`，如果 `remote_base` 里再写一次，rclone 会去请求 `/dav/dav/...`，所有文件都不存在——上传器会老老实实把全部文件重传一遍。所以 `remote_base` 只能是 URL 之后的那一段，而且必须先跑 `parity` 抽样 100% 通过才允许 `run`。

**2. Cloud Sync 的限速是"单文件"的。** 它的 `max_upload_speed` 文案写得很小：Max. upload rate for a **single file**。也就是说并发多文件时，总上行可以远超这个值。我当年被限速，很可能就是这么来的。新工具用 rclone 的**聚合** `--bwlimit`，并且 `--transfers 1`。

**3. 预算是保守记账，不是精确流量。** rclone 的 `stats.bytes` 包含失败和重试读量。实测把 `--max-transfer` 设成 1 字节时，HTTP 接收端确实只收到 1 字节，日志却记了 32768 字节——它先按缓冲读取记账，再把数据裁剪到剩余额度。所以账本里的 bytes 可能比实际发出去的多，宁可提前停，也不能超。

**4. 严格 exactly-once 做不到。** 远端接受 PUT 和本地提交 SQLite 之间没有共同事务。进程如果死在"远端已成功、本地还没落盘"的窗口里，下一次只能保守重试。这是个明确的取舍：宁可偶尔重传一个文件，也不能漏备份。

**5. 升级指纹会清空审批。** 后来我给映射指纹加上了 WebDAV `user`（同 URL 换账号应该视为不同目的地，只改密码则不该失效）。结果所有已迁移映射的指纹全部变了，而程序发现指纹不匹配时会按"新映射"处理，重新接管等于把十几万条已核实记录推翻成待传。正确的做法是**迁移指纹而不是重新接管**：写一个只改指纹字段、其它字段逐表校验不变、单事务提交、失败回滚的迁移工具。这个坑我踩过一次，后来把它做成了正式发布的脚本。

## 三个目的地，每天轮换一个

单盘故障要靠云端兜底，所以我给了两份云副本，后来加到了第三份。三个目的地各自记账，互不牵连：A 已经有的文件，不能当作 B 也已经有了的证据。

每天轮换一个目的地，用"距起始日的天数取模"算，不依赖运行时刻、不漏跑补跑、不因失败改传别家。预算 `max_transfer 20G` / `max_duration 4h` 是单次运行的额度，不是每日累计配额。

另外加了一个**异常变更保护**：拿当前扫描和一份独立的元数据基准比较，如果"原有文件被修改 + 消失"的数量超过绝对阈值（1000），或者达到 20 个且比例超过 10%，就在任何远端调用之前停下来，退出码 5，并持久保存暂停状态。跨天、换目的地、重启、重新接管都不会自动解除，必须人工核对后拿令牌 `approve-changes`。它防的是误删和批量改名，不是勒索病毒——按设计只有元数据，没有快照。

## 结果

- 日常运行的远端请求是 **0**：不上传就完全不碰网盘，开机不再有 2.5 小时的对账窗口。
- 首次接管 0 上传，之后每次只补新文件和变化文件。
- 失败有指数退避（1、2、4、8、16 分钟，带抖动）、目的地冷却和显式重置；重试状态跨重启保留。
- 账号、密码、映射都用 SHA-256 指纹绑定，改了路径或换了账号，旧的成功记录不会继续生效。

代码只用了 Python 标准库、SQLite 和 rclone：主程序四千多行，配套测试五千行（246 项，其中 14 项会起一个本地 `rclone serve webdav` 做真实传输验证）。还有一个可选的本地状态页面，同样零依赖，不扫描目录、不访问网盘。
