这篇文章不是 Agent 的入门科普，而是我在实际开发和翻源码之后，关于“怎么把 Agent 做扎实”的十条理解。它们大多不是“能不能做”的问题，而是“怎么取舍”的问题——工具怎么设计、上下文怎么省、模型怎么选、缓存怎么不踩坑。

如果只记一句话，我希望是这句：**Agent 的工程质量，很大程度上是在有限的上下文预算里做取舍。**

为了后面讨论方便，先把概念对齐。`Agent = LLM + 工具 + 循环`。LLM 本身只会“说”，Agent 还要“做”：调用工具、读取信息、修改文件、发请求，然后根据工具返回的结果继续推理，再决定下一步做什么，如此循环，直到任务完成。

和普通的 LLM 对话相比，Agent 多了三个关键能力：

| 能力                     | 说明                                            | 举例                                        |
| ------------------------ | ----------------------------------------------- | ------------------------------------------- |
| 工具调用（Tool Use）     | LLM 调用外部工具来感知和操作环境                | 读文件、跑命令、查数据库、调 API            |
| 自主决策（Autonomy）     | LLM 自己决定下一步做什么，而不是人一步步指挥    | 不是“先读 A 再读 B”，而是它自己判断该读什么 |
| 多轮循环（Agentic Loop） | 不是一次调用就结束，而是“思考→行动→观察→再思考” | 改完代码跑测试，测试挂了自动排查修复        |

这就是 Agent 和普通 ChatBot 最大的区别：ChatBot 主要是“回答”，Agent 还要“行动”。

下面十条，基本按“要不要做 → 怎么设计 → 怎么省钱 → 怎么观测”的顺序展开。

## 1. 先 Workflow，再 Agent

不是所有问题都需要一个全自主的 Agent。**能用确定性 workflow 解决的问题，优先用 workflow。**

- **Workflow**：LLM 和工具按预定义的代码路径编排，流程是写死的
- **Agent**：LLM 自己决定走哪条路、用什么工具

判断标准也很简单：这条流程你能不能提前穷举出来？能，就用 workflow。只有当“下一步该做什么”本身就需要模型动态判断时，才值得上 Agent。

全自主是有代价的——更难调试、更难评测、更贵、更容易跑偏。先用 workflow 把能确定的都确定下来，只把真正需要判断的那一小段交给 Agent，通常比一上来就全自主更稳。

## 2. 工具定义也是上下文，能少放就少放

工具定义是要进模型输入的，所以工具不是“零成本的能力扩展”。它至少带来两个问题：占用上下文，以及稀释模型的注意力。

Anthropic 的文档给了一个经验值：可用工具超过 30～50 个之后，模型选错工具的概率会明显上升；当工具数量达到 10 个以上，或者工具定义超过 1 万 token，就值得考虑按需加载。

所以主流 Agent 运行时都做了“延迟加载”。以 Claude API 的 tool search 为例：请求里仍然带着全部工具定义，但标了 `defer_loading: true` 的工具不会进入系统提示的前缀。模型一开始只看到搜索工具和非延迟工具；需要时按名字或描述检索，命中后 API 再把完整定义以 `tool_reference` 的形式追加到对话里。Claude Code 侧的对应能力叫 MCP tool search，在支持 tool search 的模型上默认开启，可以用 `ENABLE_TOOL_SEARCH=false` 关掉。

这里的关键不是“只暴露一个工具”，而是：**延迟的工具不进前缀，完整定义按需追加。** 这样既省上下文，也不会因为中途加工具而破坏缓存——追加发生在已有前缀之后，前面的内容不用重算。

启示很直接：**工具的“数量”和“体积”本身就是要管理的成本，不是免费的能力扩展。** 如果你自己写 Agent，工具一多，就该考虑类似的按需加载，而不是无脑全量塞进去。

## 3. 上下文不是“越大越好”，注意力是稀缺资源

长上下文 ≠ 高质量上下文。模型对上下文的注意力并不是均匀的——**首尾的信息注意力最高，中间最容易丢**（这就是常说的 lost in the middle）。

换句话说，你塞进去的每一条信息都在和别的信息竞争模型的注意力。无效信息越多，关键信息被忽略的概率越高。

几条被验证有效的做法：

1. **把探索过程隔离到子 Agent 去执行。** 让子 Agent 去做大量的搜索、浏览、试错，只把结论交回主 Agent。子 Agent 有自己的上下文和缓存，父级看到的只是追加的调用和结果，主上下文不会被过程细节污染。
2. **工具返回摘要，别全部回灌。** 比如 web search 工具，不需要把原文整篇返回，只返回总结性信息就够了。工具的异常报错也不该返回全量堆栈——那会占用大量无效上下文。
3. **完成阶段性任务要及时摘要。** 别让原始细节一直占着上下文，工具调用的结果要在合适的时机压缩掉。

再往前一步，是分清三种“记忆”手段：**上下文编辑**（清掉过期的工具结果和思考块）、**压缩**（接近上限时把早期内容摘要掉）、**外部记忆**（跨会话持久化）。它们解决的不是一回事，长跑任务通常三者都用。

## 4. 工具描述要写“调用策略”，不是写“功能说明”

工具描述是给模型做路由决策用的。写描述时，可以想想你会怎么给团队新来的同事介绍这个工具——把那些隐含的领域知识、专业术语、资源之间的关系都写出来。

一份好的工具描述，至少要回答四个问题：

- **做什么**
- **什么时候用**
- **什么时候不用**
- **和相似工具的边界在哪**

最后一条最容易被忽略，也最关键。如果你有两个功能相近的工具，描述里不写清楚“什么情况该选谁”，模型就只能靠猜。

工具名和参数名也会参与搜索匹配，所以命名要尽量可检索、成体系，比如统一加 `github_`、`slack_` 这样的前缀，别用一堆只有内部人才懂的缩写。

如果工具会改变外部状态——发消息、删数据、调外部 API——描述里还要写清楚副作用和是否可逆。这不是文档礼貌，而是 harness 决定“要不要加人工审批”的依据。

**Skill 也是同理。** skill 的 description 常驻在上下文里，正文等真正用到时才加载。所以 description 里最好也写清楚什么时候该调用、什么时候不该用——它和工具描述一样，本质上都是给模型看的“路由表”。

## 5. 工具要面向 Agent 设计，别照搬后端 API

面向 Agent 的工具，不应该只是后端 API 的一层薄包装。

后端 API 是按“资源”和“职责”拆分的，一个完整业务动作往往要串好几个接口。但让 Agent 自己一步步拼这些中间步骤，既费 token 又容易出错。**把常见的链式调用合并成一个工具**，是更贴合 Agent 的设计。

另一个更进一步的思路是 **programmatic tool calling**：让模型不直接一个接一个地调工具，而是在代码执行环境里写一段脚本，把多次工具调用编排进去。工具的返回值回到脚本里处理（循环、过滤、分支），只有脚本的最终输出才会回到模型的上下文。这样一来，中间那堆数据根本不会污染上下文，往返次数也大幅减少。

顺带把两种“省上下文”的手段分清楚：tool search 省的是**工具定义**，programmatic tool calling 省的是**工具结果**。两者解决的不是同一个问题，可以叠加使用。

还有一个常被忽略的点：**错误也是上下文。** 工具失败时，不要只抛一个堆栈或一句 `error`，而要返回模型能据此恢复的信息：哪个参数不对、可选值是什么、下一步可以怎么改。把错误当成一次正常的工具结果返回，而不是让整个循环崩掉，Agent 才有机会自我修复。

设计工具时，多问一句：**这个工具是给“人”用的封装，还是给“模型”用的能力？** 两者的最优形态往往不一样。

## 6. 模型要分层路由，别什么都上最强

不是所有任务都值得上最强的模型。搜索、分类、抽取这类任务，小模型往往已经够用；但“质量差距可以忽略”不能拍脑袋，最好用一批真实任务测一下再决定。

| 任务类型           | 推荐层级                    | 为什么               |
| ------------------ | --------------------------- | -------------------- |
| 文件搜索、简单查找 | 小模型（如 Haiku）          | 便宜快，多数场景够用 |
| 代码编写、常规推理 | 中档模型（如 Sonnet）       | 性能和成本的最佳平衡 |
| 架构决策、复杂规划 | 旗舰模型（如 Opus / Fable） | 需要深度推理         |

小模型和旗舰模型之间常常差几倍，极端情况下能到十倍。一句“什么都上最强”，账单会很难看。

成熟的 Agent 系统几乎都会做分层路由。Claude Code 的子 Agent 就支持按模型解析，顺序是：**单次调用指定 → 子 Agent 配置里的 `model`（`inherit` 表示继承主会话）→ `CLAUDE_CODE_SUBAGENT_MODEL` 环境变量 → 主会话模型**。这个顺序在 v2.1.251 调整过，环境变量不再压过前两者。

**Explore 子 Agent 的模型策略也变了。** 从 v2.1.198 起，内置 Explore 改为继承主会话模型，不再固定用 Haiku。想省钱，可以自定义一个同名 Explore 子 Agent 并写 `model: haiku`，而不是假设内置的一定用 Haiku。

还有一个和缓存相关的取舍：**主循环正在用某个模型时，中途切模型会让缓存全部失效。** 要省钱，正确做法是“派一个用更便宜模型的子 Agent 去做子任务”，而不是把主循环的模型换掉——子任务是独立的前缀，主循环的缓存可以保住。同理，在多数模型上，中途改 effort、开或关 fast mode 也会触发缓存重建；能在一开始定好的设置，就别在任务中途改。

有的用户量大的 Agent，甚至会专门加一个路由层，先判断用户问题的复杂度，再决定路由到哪个级别的模型。这有用，但路由本身也有成本和误判：多一次判断就多一次调用，判错还会让强模型做小事、弱模型做难事。先从简单的规则或固定分层开始，有数据再上路由模型。

## 7. 内容顺序很重要：缓存是前缀匹配，改一个字后面全废

LLM API 是无状态的，每次调用都要把上下文全部重新传一遍：System Prompt、工具定义、历史消息……为了省钱，各家都提供了 prompt caching。

但缓存是按**前缀**匹配的：模型看到的顺序是 `工具定义 → System → 消息`，从这个顺序的第一个 token 开始必须完全一致，中间任何一个字节变了，**它后面**的所有缓存全部失效。

由此得到一条核心原则：

`变化频率低的东西放前面，变化频率高的东西放后面。`

**坑 1：在 System Prompt 里塞动态内容。** 有人在 System Prompt 顶部写了 `Today is ${new Date().toISOString()}`。结果每次请求前缀都不一样，缓存永远命中不了。解决办法：时间戳、请求 ID 这类动态信息不要放在系统提示词里，放到后面的 messages 里——在支持的模型上，用一条“中途插入的 system 消息”是更好的选择，它位于历史之后，既不影响缓存，又保留操作者指令的语义。

**坑 2：对话中途换工具集或换模型。** 工具定义位于前缀最前面，增删非延迟工具会改写前缀；切换模型则因为缓存按模型隔离，也会让之前的缓存全部失效。所以尽量让工具集和模型在整个会话内保持稳定。开启 tool search 后，MCP 工具默认是延迟加载的，中途接入服务器通常不会动前缀；真正会破坏缓存的是非延迟工具集的增删，或者关掉 tool search 后加工具。

**顺带说清楚一个边界：** 并不是“装个新 skill / 新命令就必须新开会话”。skill 和命令是在调用时以用户消息的形式注入的，对缓存是安全的；插件带的 skills、commands、agents 等也不会让缓存失效，`/reload-plugins` 就能生效。插件如果带 MCP server，则按 MCP 的规则算。真正需要重启会话的，通常是改动了 **MCP server 的配置**——连接断了可以用 `/mcp reconnect`，但配置变更要重启后才会重新读取。

另外两个实用细节：**能缓存的最小前缀长度和模型有关**，大致在 512～4096 token 之间，而且并不是越新越短——Opus 5 / Fable 5 是 512，Opus 4.6 / Haiku 4.5 是 4096。太短的前缀根本不会缓存，加了标记也没用。想确认缓存到底有没有命中，看响应里的 `usage` 字段：如果 `cache_read_input_tokens` 一直是 0，那多半有个“隐形杀手”在偷偷改动前缀。Claude Code 用户可以直接看 `/usage` 里的 Prompt cache 统计（v2.1.251+）：命中率、miss 次数、缓存是否还热；能判断原因时，它还会给出最近一次 miss 的可能原因（v2.1.260+）。

## 8. 上下文不是数据库

我们很容易习惯性地把所有信息都塞进上下文里传来传去。但 LLM 的上下文应该只保留**当前推理所需的关键信息**，不该承担数据存储的职责。

典型的“不该塞进上下文”的数据：

- 图表数据
- 大批量查询结果
- 中间计算结果
- 当前的状态信息

这些东西完全可以放在数据库、Redis 或对象存储里，上下文里只保留 ID、摘要或关键结果。Agent 需要时，再通过工具按 ID 或 session 信息动态取回。

举个具体的例子：一些图表数据，可以存进数据库，只把数据 ID 返回给模型；业务页面通过 ID 去查全量数据。再比如一些中间变量，不必全靠上下文传递，可以绑定到 sessionId 之类的关键信息上，需要时再取。

跨会话的状态则交给 memory 工具或外部存储，不要靠“把历史全带上”来维持连续性。

这样做既降低 token 消耗，也减少无关信息对模型推理的干扰。核心思想是：

`让 LLM 负责思考，让存储系统负责记忆，让工具负责获取数据。`

Agent 不是简单的 ChatBot——它可以借助外部存储，而不是完全依赖上下文来传递全部信息。

## 9. AGENTS.md / CLAUDE.md 别写太长，做索引就好

项目级的指导文件（`AGENTS.md`、`CLAUDE.md` 这类）不适合无限膨胀。

它们一旦变长，就会同时带来两个问题：一是每次都占用大量上下文，二是把真正重要的规则淹没在细节里。

更合适的方式是把它们当成**入口 + 索引**：只写最关键的约定和指针，具体内容让 Agent 按需加载。Claude Code 的文档建议把 `CLAUDE.md` 控制在 200 行以内，把特定工作流的细节移到 skill 里——skill 的 description 常驻上下文，正文只在调用时加载。这就是所谓的**渐进式披露**。

同样的道理，也适用于工具描述、参考文档、规则文件。**常驻上下文的应该是“目录”，不是“正文”。**

## 10. 把上下文预算变成可观测指标

前面九条都在讲“怎么省”，但省得对不对，不能靠感觉。上下文是一个会持续增长的系统，必须有仪表盘。

至少盯四个数：

- **每轮请求的输入 token**：是只增加了本轮的新内容，还是每次都在重读整段历史？
- **缓存命中率**：`cache_read_input_tokens` 占比多少？如果长期为 0，先查前缀是不是被动态内容改坏了。
- **上下文增长速度**：同样类型的任务，跑十轮之后上下文涨了多少？涨得最快的是工具结果、文件读取，还是模型自己的输出？
- **工具结果的体积**：哪些工具一次就回灌几千 token？它们最值得做摘要或外置。

在 Claude Code 里，`/usage` 会给出会话的 token 和 Prompt cache 统计，`/context` 能看到当前上下文被什么占用；如果要跨用户、跨机器看，OpenTelemetry 会导出 cache read/creation token 等指标。自己写 Agent 的话，至少把每次响应的 `usage` 记下来，按会话聚合。

再往前一步是评测：准备一批有代表性的任务，记录成功率、token 成本、延迟。每次改 prompt、改工具描述、换模型，都跑一遍。没有评测，你很难判断一次“优化”到底是省了钱，还是把问题推到了下一轮。

**可观测性不是运维的事，它是上下文取舍的一部分。** 看不见的预算，最后都会以账单或质量下降的形式出现。

## 结语

回头看这十条，它们其实是同一个约束的不同侧面：**上下文预算是有限的，而 Agent 的每一处设计都在决定“什么东西值得占用它”。**

工具要延迟加载，是因为工具定义也占上下文；子 Agent 要隔离，是为了不让过程细节污染主上下文；工具要返回摘要，是为了别把原文硬塞回来；数据要外置，是因为上下文不该当数据库；缓存要按前缀排布，是因为稳定的前缀才能被复用；指导文件要做索引，是因为常驻的应该是目录而不是正文；最后要可观测，是因为你无法优化看不见的东西。

想清楚“这条信息，此刻真的需要出现在模型面前吗”——很多设计问题就有了答案。

少即是多。
